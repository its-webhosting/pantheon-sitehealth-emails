# Independent adversarial review — `apply-platform-domains-cloudflare`

**Reviewer:** fresh-context `psh-reviewer`, 2026-08-04. Read in full before touching the artifact:
`prompts/directives.md`, `prompts/adversarial-review.md`, `CLAUDE.md`,
`development/2026-08-03-platform-domain-util4/{PROMPT,SPEC,PLAN}.md`, the script, its test file,
both siblings, and `development/2026-07-31-platform-domain-util3/SPEC.md` §5.4/§5.5. The installed
SDK (`/workspace/.venv/lib/python3.13/site-packages/cloudflare/`, 5.4.0) was read directly rather
than trusted from the docstrings.

## Verdict

This is the strongest test suite I have reviewed in this repo. I ran **25 deliberate mutations** of
the production code against the 211-test file; **22 went red**, including every one I expected to be
vacuous (the dry-run zero-write gate, all four environment-pin routes, the `changed_count` formula,
the `2`-vs-`3` rule in all three failure arms, the record-name cross-check, the sorted-key-order
loop, the duplicate-key detection, `require_usable_streams`, both stream-guard detaches). The
production code is careful and the reasoning in the docstrings is, on the points I could check,
accurate against the installed SDK.

It does not pass. **One Critical finding breaks the script's central promise**: exit 2 means
"nothing in Cloudflare was changed", and I have a reproduced run where a batch call was made,
returned, and the process exited 2 while its run record recorded the entry as `not-attempted`. Two
Important findings are the PD#14 shape this branch's own §22 names as its dominant failure class —
a property the code has and the instrument cannot go red on — and one of them covers the exact
sentence `PROMPT.md` is most explicit about ("it should not attempt to make the remaining changes").
Three more Important findings concern the verification model, the SDK-retry pin's absence from every
governing document, and acceptance evidence that describes a tree three commits old.

**Every file I edited is restored.** I created and deleted `tests/unit/test_zzz_review_probe.py`,
and all mutations were applied and reverted by scripts that rewrite the original text at the end;
`git diff --stat apply-platform-domains-cloudflare tests/unit/` is empty and the focused suite is
211/211 green at the end of the review. `git status` shows one modified file, `monthly-report.txt`,
which is **not mine** — it changed under me during the session (another agent in this workspace) and
I did not touch it. I ran no `--for-real` invocation and made no live API call of any kind.

## Findings

### 1. CRITICAL — exit 2 can lie: an exception raised *after* the batch call has returned leaves the entry `not-attempted`, so `changed_count()` sees 0

**File/line:** `apply-platform-domains-cloudflare:1229-1275` (`apply_all`'s handler chain),
reached from `apply_entry` at `:1121-1153`.

**Claim.** `apply_all` catches exactly `KeyboardInterrupt`, `(cloudflare.APIConnectionError,
TimeoutError, OSError)`, `VerifyError` and `ApplyError`. Anything else raised from inside
`apply_entry` propagates out with the entry's outcome still at its `not-attempted` seed. If that
exception is raised on a code path *after* `client.dns.records.batch(...)` returned — i.e. after
Cloudflare committed the transaction — `changed_count()` cannot see the change, and
`failure_code(state)` returns **2**, the code SPEC §8 defines as *"Could not complete, and **nothing
in Cloudflare was changed**"*.

**Concrete failure scenario.** A one-entry plan, `--for-real`. The batch POST succeeds (HTTP 200,
Cloudflare has swapped the CNAME for the A records). The post-apply verification `list` call then
gets a 200 whose body is truncated or not JSON — the SDK calls `response.json()` with no guard:

```
/workspace/.venv/lib/python3.13/site-packages/cloudflare/_response.py:266
        data = response.json()
```

`json.JSONDecodeError` is a `ValueError`, not a `cloudflare.CloudflareError`, not an `OSError`. The
same shape arises from an `AttributeError`/`KeyError` on an SDK model change at `:1149`
(`[r.id for r in governed_records(rows)]`) — the exact scenario SPEC §8.3 names: *"An
`AttributeError` or `KeyError` from an SDK shape change is precisely what this arm exists to catch,
and it can land after entries have applied."* The arm catches it; the *tally* does not know an entry
was touched.

**Evidence (reproduced).** Temporary probe test, one entry, fake client whose `batch()` succeeds and
whose verification `list()` raises `ValueError("Expecting value: line 1 column 1 (char 0)")`:

```
EXIT: 2
BATCH CALLS MADE: 1
OUTCOME: {'outcome': 'not-attempted'}
MODE LINE: ['  mode:   FOR REAL -- 0 of 1 entries changed']
STDERR: FOR REAL -- changes WILL be made to Cloudflare
        ERROR: unexpected ValueError: Expecting value: line 1 column 1 (char 0)
```

Three artifacts lie at once: the exit code (`2` = nothing changed), the `mode:` line (`0 of 1
entries changed`) and the run record (`not-attempted`, which SPEC §12.2 defines as *"never reached,
because an earlier entry failed"*). CLAUDE.md's own claim is falsified by this run:

> "No failure path — not a validation abort, not an `InvariantError` from this script's own
> reasoning, not the `except BaseException` last line of defence — may report `2` once anything has
> actually changed; every one of them is routed through `changed_count()` first."

Routing through `changed_count()` is necessary but not sufficient: nothing records that the entry
was attempted.

**Refutation attempted.** I checked whether `_strict_response_validation` would convert this into
`APIResponseValidationError` (an `APIError` → `CloudflareError`, which *would* be caught): it would
not — `_base_client.py:692` gates that on `self._strict_response_validation`, which the client is
built without (`build_client` at `:784` passes only `base_url` and `max_retries`). I checked whether
the existing catch-all test covers it: `test_a_plain_exception_mid_apply_after_an_applied_entry_
exits_three_not_two` (`:3166`) raises **instead of** `apply_entry`, so nothing committed and its
exit 2/3 assertion is about a different state; it also uses three entries so an earlier `applied`
masks the arithmetic. I checked whether `merge_body`/`verdict_for`'s `InvariantError` guards cover
it: they are `StartupError` subclasses and fire *before* the batch call. No guard exists.

**Fix direction.** Give `apply_all` a final `except BaseException` arm (or wrap the `apply_entry`
call in one) that marks the in-flight entry — the same thing the `KeyboardInterrupt` arm at `:1231`
already does for exactly this reason. The correct outcome is `unknown` if the exception can have
been raised before the batch returned, and `unverified` if `apply_entry` can tell it happened after;
the cheapest total fix is for `apply_entry` to set a "batch returned" flag the caller reads, or to
convert its post-batch section into a `try:` that re-raises anything unrecognised as `VerifyError`
(which SPEC R6.3's reasoning already licenses: *"the transport failing is not evidence the batch did
not commit"*). Then re-raise, so `main()`'s last line of defence still names the class. Add a test
with a **single** entry so the arithmetic cannot be masked.

### 2. IMPORTANT — "stop at the first failure" is untested for the `unverified` and `unknown` arms; both `return`s can be deleted with the suite green (PD#14)

**File/line:** `apply-platform-domains-cloudflare:1251` (unknown arm) and `:1267` (unverified arm).

**Claim.** `PROMPT.md` is verbatim on this: *"it should not attempt to revert any changes it has
already made, and it should not attempt to make the remaining changes specified in the file."*
SPEC R3.4 restates it. The `failed` arm's `return` is pinned (`test_a_failure_on_the_second_entry_
leaves_the_third_not_attempted`, three entries, `assert len(client.batch_calls) == 2`). The
`unverified` and `unknown` arms' `return`s are **not** — every test that reaches them uses a
one-entry document (`plan_doc()`), where `return` and `continue` are indistinguishable.

**Evidence (mutation).** Replacing `return` with `continue` in either arm:

```
GREEN | apply_all UNVERIFIED arm continues instead of stopping | 211 passed in 5.25s
GREEN | apply_all UNKNOWN arm continues instead of stopping    | 211 passed in 5.69s
RED   | apply_all FAILED arm continues instead of stopping     | 2 failed, 209 passed
```

The mutation is a real behaviour change, not a no-op. Driving the mutated script through `main()`
with a three-entry plan whose second entry raises `TimeoutError` from `batch()`:

```
--- WITH the return->continue mutation ---
a.umich.edu  applied
b.umich.edu  UNKNOWN -- the call did not complete (TimeoutError: dropped)
c.umich.edu  applied                              <-- a THIRD zone rewritten past the failure
  applied 2 ... unknown 1 ... not attempted 0
exit: 3  batch zones called: ['z-a', 'z-b', 'z-c']

--- unmutated ---
a.umich.edu  applied
b.umich.edu  UNKNOWN -- the call did not complete (TimeoutError: dropped)
  applied 1 ... unknown 1 ... not attempted 1
exit: 3  batch zones called: ['z-a', 'z-b']
```

So a regression that keeps rewriting production DNS after an entry of unknown fate — the single
behaviour `PROMPT.md` forbids most explicitly — ships green.

**Refutation attempted.** I looked for any three-entry `unverified`/`unknown` fixture: the only
multi-entry pass-3 fixtures are `three_entry_doc()` uses at `:2315`, `:2354`, `:2419`, `:3133`,
`:3166`, and all of them drive the `failed`, `InvariantError` or `RuntimeError` paths. I checked
whether `assert "unknown 1" in out` (`:2455`) or the whole-record equality at `:2486` could catch it
— they cannot; with one entry there is no later entry to leak into the tally.

**Fix direction.** Promote `test_a_connection_error_...` and `test_a_verify_mismatch_...` to
`three_entry_doc()` with the failure on `b.umich.edu`, and assert both `len(client.batch_calls) == 2`
and `record["entries"]["c.umich.edu"]["outcome"] == "not-attempted"` — the same shape the `failed`
test already uses. (This is the same class SPEC §22 names: *"an assertion on a failure path that can
be deleted with the suite green. The second appeared in seven of the ten tasks."* This is the eighth
and ninth instance.)

### 3. IMPORTANT — `proxied` is invisible to both the `already-applied` verdict and the post-apply verification, so a DNS-only record verifies as a correct rewrite

**File/line:** `record_key` at `:476-498`, `verify_records` at `:1062-1085`, `verdict_for` at
`:574-582`. Spec basis: §7.1's comparison key and R6.1.

**Claim.** R6.1 is justified by PD#14 — *"A 200 from the batch endpoint is Cloudflare's CLAIM that
the swap happened; the record list is the EVIDENCE"* (`apply_entry` docstring). But the evidence
collected is only `(TYPE, normalize(name), canonical_content)`. `proxied` — the field whose loss is
the migration's worst outcome — is read from the list response by nobody. Neither SPEC nor PLAN
mentions `proxied` in the verdict or verification model at all (`grep -n proxied SPEC.md PLAN.md`
returns only the §11.4 example line and the data flow prose), so this is an untraced gap rather than
an argued decision.

**Concrete failure scenarios.** (a) An operator (or an automation) turns the orange cloud off for a
rewritten FQDN. Re-running the same plan file — the action R4.2's `already-applied` carve-out exists
to make safe, and CLAUDE.md advertises as *"safe, cheap, and call zero Cloudflare write endpoints"* —
reports `a.umich.edu  already applied -- nothing to do`, exit 1, and the run record the operator
attaches to the change ticket says the state is correct. (b) A batch that creates the records
DNS-only verifies `True` and is reported `applied`, exit 0.

**Evidence.** Direct probe against the shipped helpers, with Cloudflare holding exactly the plan's A
record but `proxied=False`:

```
verdict_for  -> ('already-applied', '')
verify_records -> True
```

Why this matters is stated by the script that *writes* these files
(`find-platform-domains-cloudflare:537-539`):

> "`proxied` is ALWAYS emitted: its API default is false, and a replacement created DNS-only would
> take the hostname out of certificate service ('Cloudflare can only serve an SSL/TLS certificate
> for a DNS record when you set the record's proxy status to Proxied')."

A DNS-only replacement is an HTTPS outage plus origin-IP exposure. The applier's strongest
instrument cannot see it.

**Refutation attempted.** I checked that the data is actually available: the SDK's record models
carry `proxied` (the main program's `plugin/cloudflare/fqdns.py` already reads it, and CLAUDE.md
documents the null-vs-false distinction), so no extra API call is needed. I checked whether
`describe_change`'s `(proxied, ttl N)` block covers it — that is derived from the *file*, never from
Cloudflare, so it reports what was intended, not what exists. I considered whether the omission is
deliberate for the D side: it is *necessary* there, because `delete_match` items are
`{type, name, content}` only (`find-platform-domains-cloudflare:613-617`, `:594-600`) — but that is
an argument for leaving `record_key` alone, not for leaving the P side unchecked.

**Fix direction.** Do **not** widen `record_key` (it must stay comparable against `delete_match`).
Add a separate P-side flag check used by `verify_records` and by the `already-applied` branch of
`verdict_for`: for each post, require the matching live record's `proxied` to equal
`bool(post["proxied"])`. A mismatch on verification is a `VerifyError` (Cloudflare committed, the
result is not the intended one — exactly `unverified`); a mismatch at validation time is a new
invalid verdict, or at minimum demotes `already-applied` to `records-missing`/a new
`proxy-status-drift` code so the run refuses rather than skipping. Update SPEC §7.1/§7.3/R6.1, which
currently do not contemplate the field.

### 4. IMPORTANT — `max_retries=0`, the write-side safety pin, is recorded in no governing document; SPEC §17 still says there is "one deliberate divergence" from the sibling's `build_client`

**File/line:** `apply-platform-domains-cloudflare:784`; SPEC §17's table row and the paragraph
beginning *"`build_client`'s credential-nulling test diverges from both other copies"*; CLAUDE.md's
`apply-platform-domains-cloudflare` subsection and the `find-platform-domains-cloudflare`
subsection's "three places to check".

**Claim.** An AST-level diff of every copied helper against `find-platform-domains-cloudflare`
(docstrings ignored) shows `build_client` has **two** divergences, not one:

```
-    client = Cloudflare(**creds, base_url=API_BASE_URL)
+    client = Cloudflare(**creds, base_url=API_BASE_URL, max_retries=0)
-        if field not in creds:
+        if creds.get(field) is None:
```

SPEC §17 documents only the second. `grep -n "max_retries\|retries" SPEC.md` returns nothing about
the constructor pin; `grep -n max_retries CLAUDE.md` returns nothing at all. The property exists
only in the script's own docstring and one test.

**Why it matters.** This is the property that keeps the SDK from silently re-POSTing a
**non-idempotent** batch. Verified against the installed SDK: `_base_client.py:1094-1097` retries on
`httpx.HTTPStatusError` whenever `_should_retry(response)` is true, with no HTTP-method check, and
`Cloudflare`'s own default is 2 retries. A retried `POST /dns_records/batch` whose first attempt
committed produces a *second* error (duplicate-create 400) that this script would classify `failed`
— "rejected, nothing committed" — for a write that committed. That is finding 1's failure mode
arriving by a different door, and it was found late (the script docstring calls it "CRITICAL 1
(whole-branch review)"). CLAUDE.md tells a future maintainer there are *"three places to check"* on
an SDK upgrade and implies the three are the same pin; they are now three materially different
implementations, and only one of them defends a write path.

**Refutation attempted.** I confirmed the property is tested
(`test_build_client_pins_max_retries_to_zero` plus a real-`httpx.MockTransport` test asserting one
POST on a 429/500), so this is a documentation defect, not a code defect. I checked whether SPEC §16
or §14 group 13 cover it obliquely — they cover the four credential routes only. I checked whether
§19's deletion checklist depends on it — it does not.

**Fix direction.** Add `max_retries=0` and its reasoning to SPEC §17's divergence paragraph (and
change "One deliberate divergence" to name both), and to CLAUDE.md's subsection beside the
"only copy that performs writes" sentence, so the SDK-upgrade checklist covers the retry pin as well
as the four credential routes. Also state in CLAUDE.md that the three copies are no longer identical
and which one is deliberately left on the old `field not in creds` idiom (SPEC §17 records this;
CLAUDE.md does not).

### 5. IMPORTANT — the applier ignores `generated.zones_swept`/`zones_total`, so a plan built from a narrowed sweep is applied and recorded with no signal

**File/line:** `run_once` at `:1609` reads only `doc["generated"].get("at", "unknown")`;
`outcome_document` at `:1412-1418` records only `source_generated_at`.

**Claim.** The file's own header is written to be checked. `find-platform-domains-cloudflare`'s
`provenance()` docstring (`:911-914`) states the intent explicitly:

> "The ranges and the suffix are recorded so an applier can verify the assumptions the file was
> built under, and `direction` so it can refuse the wrong file outright."

The applier verifies `direction` and nothing else. CLAUDE.md says of a subset sweep written with
`-o`: *"a narrowed run written that way emits a loud `ATTENTION: … covers N of M zones … MUST NOT be
used as the baseline for a rewrite`"* — a warning on the generating run's stderr, which scrolls away.
The machine-readable evidence survives in the file (`zones_swept` vs `zones_total`), and the applier
— the last program to see the file before production DNS changes — drops it.

**Concrete failure scenario.** An operator generates `/tmp/one-zone*` while testing
(`./find-platform-domains-cloudflare -v -o /tmp/one-zone engin.umich.edu`), then a week later
applies `/tmp/one-zone-plan.json` believing it is the org-wide baseline. The run succeeds, exits 0,
and the run record — SPEC R9.2's *"thing an operator can attach to a change ticket"* — contains no
trace that the source covered 1 of 187 zones. The same applies to the matching revert file, which is
the artifact an incident response would reach for.

**Refutation attempted.** I checked whether this is destructive rather than merely incomplete: the
entries themselves are correct, so no wrong record is written — the harm is a silently partial
rewrite and a change record that cannot be audited. I checked whether `--only`'s ATTENTION covers it
(it reports narrowing *this run* applied, not narrowing baked into the file). I checked whether SPEC
§20 declines it: §20 declines re-resolution and re-walking zones, not reading the header the file
already carries.

**Fix direction.** In `run_once`, after `check_file_contract`, read `generated.zones_swept` and
`generated.zones_total`; when they differ, print an unconditional
`ATTENTION: this file was generated from a PARTIAL sweep (N of M zones) and MUST NOT be treated as a
complete baseline` on stderr, mirroring the sibling's own wording. Carry both numbers into the run
record's `run` block beside `source_generated_at`. Both are free — no extra API call, no DNS.

### 7. MINOR — a raise from `finish()`'s unguarded prologue escapes `main()` entirely and CPython exits **1**, the one code the handler chain exists to route away from

**File/line:** `apply-platform-domains-cloudflare:1552-1555` (`signal.signal`, `now_utc()`,
`tally()`, `outcome_path()` — all outside the two `try` blocks below them) and `failure_code` at
`:969`, which calls `tally` again from *inside* `main()`'s `except` clause.

**Claim.** `tally()` raises `InvariantError` on an out-of-vocabulary outcome (`:934`). If that fires
inside the first `finish()` call, `main()`'s `except StartupError` calls
`finish(failure_code(state), …)`; `failure_code` calls `tally` again, raises again — now *inside* an
`except` clause, which Python never redispatches to a sibling `except` of the same `try`. The
exception escapes `main()`, the interpreter prints a traceback and exits **1**.

**Evidence (reproduced).** Probe with `tally` replaced by a raiser:

```
ERROR: contrived bookkeeping defect
ESCAPED main() as InvariantError -> CPython would exit 1 (uncaught traceback)
```

SPEC §8.3: *"CPython exits **1** on any uncaught traceback, and 1 here means 'completed with
already-applied skips'. Without this guard a crashed run and a healthy run are indistinguishable."*
The guard exists; this path steps around it.

**Refutation attempted.** I traced every statement in the prologue for a *live* trigger and found
none: `outcome_path` is documented and tested total over pathological `FILE` values, `now_utc`
cannot fail, `signal.signal` has no thread hazard here, and every outcome string assigned in the
program is an `OUTCOMES` literal. So this is latent, requiring an upstream defect — which is exactly
the situation `InvariantError` exists for, and exactly when an operator most needs the exit code to
be honest. Marked Minor for that reason, not dismissed.

**Fix direction.** Move the prologue inside `finish()`'s existing `try`, or wrap `finish()`'s whole
body in `try/except BaseException` that reports the class through `report_line` and returns the
already-computed `code`. Cover it with a test that monkeypatches `apc.tally` to raise and asserts
`main()` returns 2/3, never 1.

### 10. MINOR — nothing warns on a stale plan, and the staleness that matters is invisible to validation (argument against SPEC §20's decision)

**File/line:** SPEC §20 row 1 (*"Re-resolving each plan entry's target to detect a stale plan —
Offered as an expansion and **declined**… the file is the authority"*); `summary_lines` at `:1020`
prints `generated.at`.

**Argument.** I am not asking for re-resolution — §20's reasoning against a DNS dependency holds.
But the mitigation §11.3 claims (*"The age of the file is therefore the operator's only staleness
signal, so it is printed on every run"*) is weaker than it reads. Validation compares R against
**D** (the CNAME), so a plan whose **P** addresses have gone stale validates perfectly `ready` and
then writes the wrong addresses; the recorded project knowledge is that this happens
(`~5 distinct A/AAAA sets, rotating rrset order` — the platform-domain address-set memory note, and
CLAUDE.md's own "regenerate the baseline immediately before any rewrite"). The signal is one
undecorated ISO timestamp inside a six-line block printed **after** a 217-line report, on a run the
operator has already committed to.

**Fix direction.** Parse `generated.at` (already required to be present in practice) and, when it is
older than a small threshold, emit an unconditional stderr
`ATTENTION: this plan was generated N days ago; regenerate the baseline before a rewrite` — zero new
dependencies, zero API calls, and it lands on the stream §11.1 reserves for "problems reach a
watching operator". If the threshold is contentious, print the age in the summary's `source` line

### 11. MINOR — `describe_change` raises `InvariantError` ("a defect in this script's own reasoning") for a property of the *input file*, and does so after validation has already passed

**File/line:** `apply-platform-domains-cloudflare:1327-1332`.

not an internal invariant. PD#2 asks that the class name what triggered it and who is at fault;

the applier is broken.

**Refutation attempted.** The condition is unreachable with files the current sibling writes

loud-defect choice over rendering flags per group. I agree with rejecting per-group rendering; I
disagree with the exception class and the placement, which are separable from that argument.

**Fix direction.** Make it a ninth §6 check raising `PlanFileError`, evaluated in
`check_entry_contract` alongside checks 7/8. The message can stay as-is. That preserves the loud
behaviour, moves it before any Cloudflare read, and names the operator's file rather than the
script's reasoning.
