================================================================================
BUG REPORT
Pantheon API: the organization site-list pagination cursor (`start`) is silently
ignored for most site ids, and the first page is returned again
================================================================================

Date:           2026-07-28
Reported by:    University of Michigan, ITS Web Hosting Services
API base:       https://api.pantheon.io/v0
Endpoint:       GET /v0/organizations/{org_id}/memberships/sites?limit=&start=
Organization:   23c7208e-5f2a-4388-9fc4-5c3a038ef8b9  (408 sites at time of test)
Client:         curl 8.14.1 (aarch64-unknown-linux-gnu) libcurl/8.14.1, HTTP/2,
                direct HTTPS, no proxy
Correlation:    Responses carry no request-id or correlation header of any kind
                (verified: the failing response returned only content-type, date,
                via and alt-svc).  The machine-token exchange sends the client
                string "pagination-bug-report", which may be the only handle for
                locating these sessions in your logs.  Exact UTC timestamps of the
                run are in OBSERVED OUTPUT below.
Severity:       High.  The failure is silent: it produces a wrong-but-plausible
                result with HTTP 200 and no error, so a caller cannot detect it
                without independently knowing the correct answer.


SUMMARY
-------

The swagger for this endpoint documents:

    "Pagination is handled via query parameters (limit and start)."
    start -- "Pagination cursor (site UUID to start after)"

For most site UUIDs, `start` is not honored.  Instead of returning the sites
after the cursor, the API returns the FIRST page of the collection again, with
HTTP 200 and no error, warning, or header indicating that the cursor was
disregarded.

The cursor IS honored when the supplied id happens to be the last id of a page
the API has already returned for that organization -- which is why the obvious
"walk" pattern (pass the last id of each page you receive) works, and why the
defect is easy to miss.  Any other id silently restarts the collection.

If the intended design is that only API-issued page-boundary ids are valid
cursors, please note three things before closing this as working as designed:

  1. The API issues no cursor.  There is no cursor field in the response body and
     no Link/rel=next header, so every cursor a caller can possibly send is one
     it constructed itself from response data.
  2. The swagger defines the parameter as a "site UUID to start after", not as an
     opaque token, and every id used below is a real site UUID belonging to the
     organization being listed.
  3. CASE C below uses the id of the FIRST site in the collection -- an id the API
     itself returned, in the very page it returned it in -- and that is ignored
     too.  So "only ids we issued" does not describe the actual behavior either.

Whatever the intended cursor contract turns out to be, a cursor that cannot be
honored should produce an error rather than silently returning page 1 (see WHAT
WE WOULD LIKE, option 2).


WHAT THE OUTPUT SHOULD BE
-------------------------

Let S[1..408] be the organization's sites in the order this endpoint returns
them.  That order is ascending by site id; the reproduction script below asserts
it rather than assuming it, and stops if it does not hold.

    Request:  ...memberships/sites?limit=100&start=<id of S[101]>
    Expected: a 100-element array whose first element is S[102]

That is what "site UUID to start after" means, and it is what the endpoint does
when the cursor is the last id of a previously returned page:

    Request:  ...memberships/sites?limit=100&start=<id of S[100]>
    Expected: a 100-element array whose first element is S[101]      <-- works


WHAT THE OUTPUT ACTUALLY IS
---------------------------

    Request:  ...memberships/sites?limit=100&start=<id of S[101]>
              (concretely: start=34562508-564e-4122-9e92-38118b7fba3f)

    Actual:   HTTP/2 200
              a 100-element array whose first element is S[1]
              (concretely: 004921c4-7b9e-4f71-8649-30f5c06ed672)

              i.e. the first page of the collection, exactly as if `start` had
              not been supplied at all.  No error field, no 4xx, no warning
              header.

Reproduced 5 times out of 5 for that cursor, and 5 out of 5 for the id of S[1].
The control case (cursor = id of S[100]) succeeded 5 out of 5 in the same run.
The controls also rule out the obvious alternative explanations: if the
collection order were unstable between requests, or the session were degrading,
CASE A and CASE D could not pass in the same run in which CASE B and CASE C fail.


WHY THIS MATTERS
----------------

1. Silent truncation.  A caller that paginates with any cursor other than a
   previously-returned page boundary -- for example, resuming a long job from a
   stored site id -- receives the first page again.  With de-duplication it sees
   a short list and believes the organization is smaller than it is; without
   de-duplication it processes the same 100 sites forever.  Either way nothing
   in the response says so.

2. "Loop until an empty page" does not terminate.  Because an unrecognized
   cursor yields a full first page rather than an empty array, the standard
   termination condition for cursor pagination becomes an infinite loop.
   Callers must instead stop on a short page, which is only correct if the API
   never returns a short non-final page.

3. It defeats the natural correctness check.  A caller cannot verify its own
   pagination, because the malformed answer is indistinguishable from a
   legitimate first page.

For context, `terminus org:site:list` returns all 408 sites from a single command
invocation and is unaffected -- it does not rely on this endpoint's `start`
cursor.  The problem is specific to using this endpoint's cursor directly.


ADDITIONAL OBSERVATIONS
-----------------------

These are reported as observations, not as a diagnosis of the mechanism.

* Cursor validity tracked page boundaries.  In a positional scan of one
  organization (408 sites, limit=100), `start` was honored at positions 100,
  200, 300, 400 and 408 -- the last element of each page the API itself
  returns -- and ignored at positions 1, 2, 50, 99, 101, 102, 150, 199, 201,
  250, 299, 301, 350, 399, 401, 405 and 407.

* Cursor validity appeared to depend on earlier requests.  The id at position 50
  was ignored when tested cold, then honored consistently after a single
  `limit=50` request (for which position 50 IS a page boundary) had been made
  earlier in the same session -- including for subsequent `limit=100` requests.
  This suggests `start` is resolved against pagination the backend has already
  computed, rather than by a `WHERE id > start` predicate.

* The cursor past the end of the collection behaved inconsistently.  Using the
  id of the LAST site returned an empty array (correct) in later runs, but in an
  early run returned a full 100-element first page.

* Every observation above was made with HTTP 200 responses.  No request in any
  of these tests returned a 4xx or 5xx status.


REPRODUCTION
------------

The script below is standalone: it needs bash, curl, jq and the usual POSIX text
utilities (awk, grep, head, sed, sort, tr, wc), and reads nothing but the
credentials described in its header.  It is read-only apart from the POST that
exchanges a machine token for a session token.

  * It uses $PANTHEON_MACHINE_TOKEN if that is set, and otherwise reads the
    token from the single file in ~/.terminus/cache/tokens/.  The token is passed
    to curl on stdin, never on argv.
  * $PANTHEON_ORG_ID selects the organization, defaulting to
    23c7208e-5f2a-4388-9fc4-5c3a038ef8b9.
  * $REPEATS sets how many times each case is probed (default 5).
  * It requires an organization with at least 102 sites, and stops with a clear
    message otherwise: the probes need a site id that is provably not a page
    boundary, which needs at least two ids beyond the first page.
  * Every request is checked for HTTP 200 and the script stops on anything else,
    so a transport or authentication failure can never be misreported as a
    defect verdict.

It first collects the reference site list using the cursor pattern that works --
asserting along the way that the list is free of duplicates and ascending by id,
since every expectation below is expressed as a position in that list -- then
probes four cursors and tallies the verdicts.  CASE A and CASE D are controls
that should pass; CASE B and CASE C are the defect.  The cursors in CASE B and
CASE C are chosen so that they cannot coincidentally be page boundaries of the
caller's own pagination: position 1, and position limit+1 in a collection with at
least limit+2 elements.

An identical copy of this script is stored alongside this report as
reproduce-pagination-bug.sh.

--------------------------- begin reproduce-pagination-bug.sh ------------------
#!/bin/bash
#
# Reproduce: the Pantheon API's organization site-list pagination cursor (`start`) is
# silently ignored for most site ids -- the API answers HTTP 200 with the FIRST page
# again, instead of the page after the cursor and instead of any error.
#
# Standalone: needs bash, curl, jq and the usual POSIX text utilities (awk, grep,
# head, sed, sort, tr, wc).  Nothing else is read, sourced or imported.
#
# Credentials:
#   $PANTHEON_MACHINE_TOKEN   used if set; otherwise the single JSON file in
#                             ~/.terminus/cache/tokens/ is read (Terminus' own cache).
#                             The token is passed to curl on stdin, never on argv,
#                             so it is not visible in `ps` on a shared host.
# Organization:
#   $PANTHEON_ORG_ID          defaults to 23c7208e-5f2a-4388-9fc4-5c3a038ef8b9
# Tuning:
#   $REPEATS                  probes per case (default 5), so each verdict is a tally
#                             rather than a single sample.
#
# Requires an organization with at least 102 sites: the probes below need a site id
# that is provably not a page boundary, which needs at least two ids beyond the first
# page.  The script checks this and stops rather than reporting a misleading verdict.
#
# Read-only: every request is a GET except the POST that exchanges the machine token
# for a session token.  Every request is checked for HTTP 200 and the script stops on
# anything else, so a failure can never be mistaken for a defect verdict.
#
set -u

API="https://api.pantheon.io/v0"
PANTHEON_ORG_ID="${PANTHEON_ORG_ID:-23c7208e-5f2a-4388-9fc4-5c3a038ef8b9}"
REPEATS="${REPEATS:-5}"
LIMIT=100          # the maximum this endpoint documents
MIN_SITES=$((LIMIT + 2))

die() { echo "ERROR: $*" >&2; exit 1; }

for tool in curl jq awk grep sed sort tr wc; do
    command -v "$tool" >/dev/null 2>&1 || die "$tool is required but not on PATH"
done
case "$REPEATS" in
    ''|*[!0-9]*) die "REPEATS must be a positive integer, got '$REPEATS'" ;;
esac
[ "$REPEATS" -ge 1 ] || die "REPEATS must be at least 1, got '$REPEATS'"

# ---------------------------------------------------------------- credentials --
if [ -n "${PANTHEON_MACHINE_TOKEN:-}" ]; then
    machine_token="$PANTHEON_MACHINE_TOKEN"
    echo "Using \$PANTHEON_MACHINE_TOKEN"
else
    cache="$HOME/.terminus/cache/tokens"
    [ -d "$cache" ] || die "\$PANTHEON_MACHINE_TOKEN is unset and $cache does not exist"
    token_file=""
    count=0
    for candidate in "$cache"/*; do
        [ -f "$candidate" ] || continue
        token_file="$candidate"
        count=$((count + 1))
    done
    [ "$count" -eq 1 ] || die "expected exactly one token file in $cache, found $count -- set \$PANTHEON_MACHINE_TOKEN to choose one"
    machine_token=$(jq -r '.token // empty' < "$token_file")
    [ -n "$machine_token" ] || die "$token_file has no .token"
    echo "Using the machine token from ~/.terminus/cache/tokens/"
fi

# The token goes in on stdin (--data @-), not on the command line, so it never appears
# in the process table.
session=$(jq -n --arg t "$machine_token" '{machine_token: $t, client: "pagination-bug-report"}' \
    | curl -s -X POST -H "Content-Type: application/json" --data @- "$API/authorize/machine-token" \
    | jq -r '.session // empty')
[ -n "$session" ] || die "could not exchange the machine token for a session token"

echo "Started (UTC):  $(date -u '+%Y-%m-%d %H:%M:%SZ')"
echo "Organization:   $PANTHEON_ORG_ID"
echo "Endpoint:       GET $API/organizations/\$PANTHEON_ORG_ID/memberships/sites?limit=$LIMIT&start=<site id>"
echo "curl:           $(curl --version | head -1)"
echo "Client string:  pagination-bug-report  (sent in the machine-token exchange; responses"
echo "                carry no request-id header, so this is the only correlation handle)"
echo "Repeats/case:   $REPEATS"
echo

# ------------------------------------------------------------------- helpers --
# get_page [cursor] -> the JSON array on stdout; returns nonzero on any non-200.
# NOTE: this must RETURN rather than exit -- it is always called inside $( ), where an
# exit would only kill the subshell.  Every call site therefore ends in `|| die`.
get_page() {
    local url response status body
    url="$API/organizations/$PANTHEON_ORG_ID/memberships/sites?limit=$LIMIT"
    [ -n "${1:-}" ] && url="$url&start=$1"
    response=$(curl -s -w '\n%{http_code}' -H "Authorization: Bearer $session" "$url") || {
        echo "curl failed for $url" >&2
        return 1
    }
    status="${response##*$'\n'}"
    body="${response%$'\n'*}"
    if [ "$status" != "200" ]; then
        echo "GET $url returned HTTP $status (expected 200)" >&2
        return 1
    fi
    printf '%s\n' "$body"
}

# classify <json page> <expected first id, or EMPTY> -> CORRECT | PAGE-1-AGAIN | OTHER
classify() {
    local length first
    length=$(echo "$1" | jq 'length')
    first=$(echo "$1" | jq -r '.[0].id // empty')
    if [ "$2" = "EMPTY" ]; then
        [ "$length" -eq 0 ] && { echo CORRECT; return; }
    elif [ "$first" = "$2" ]; then
        echo CORRECT; return
    fi
    if [ "$first" = "$page1_first" ]; then echo PAGE-1-AGAIN; else echo OTHER; fi
}

# probe <label> <cursor> <expected first id, or EMPTY>
probe() {
    local label="$1" cursor="$2" expected="$3"
    local correct=0 repeated=0 other=0 i page
    for ((i = 0; i < REPEATS; i++)); do
        page=$(get_page "$cursor") || die "the probe request failed; see the message above"
        case $(classify "$page" "$expected") in
            CORRECT)      correct=$((correct + 1)) ;;
            PAGE-1-AGAIN) repeated=$((repeated + 1)) ;;
            *)            other=$((other + 1)) ;;
        esac
    done
    printf '  %-46s correct=%d  RETURNED-PAGE-1-AGAIN=%d  other=%d\n' \
        "$label" "$correct" "$repeated" "$other"
}

# ------------------------------------------------- collect the reference list --
echo "Collecting the site list, cursor = last id of each full page (the pattern that works) ..."
page=$(get_page) || die "could not fetch the first page"
page1_first=$(echo "$page" | jq -r '.[0].id')
page1_length=$(echo "$page" | jq 'length')
[ "$page1_length" -eq "$LIMIT" ] || die "this organization has only $page1_length sites; reproducing needs at least $MIN_SITES"

all_ids=$(echo "$page" | jq -r '.[].id')
cursor=$(echo "$page" | jq -r '.[-1].id')
pages=1
while :; do
    page=$(get_page "$cursor") || die "could not fetch the page after cursor $cursor"
    length=$(echo "$page" | jq 'length')
    [ "$length" -eq 0 ] && break
    [ "$(echo "$page" | jq -r '.[0].id')" = "$page1_first" ] && \
        die "the cursor was ignored while collecting the reference list; re-run"
    all_ids="$all_ids"$'\n'$(echo "$page" | jq -r '.[].id')
    pages=$((pages + 1))
    [ "$length" -lt "$LIMIT" ] && break
    cursor=$(echo "$page" | jq -r '.[-1].id')
done

total=$(echo "$all_ids" | wc -l | tr -d ' ')
unique=$(echo "$all_ids" | sort -u | wc -l | tr -d ' ')
[ "$total" = "$unique" ] || die "the reference walk itself returned duplicates ($total collected, $unique unique); re-run"
# Assert the ordering rather than asserting it in prose: every "expected first id" below is
# a POSITION in this list, so if the collection were not totally ordered and stable, those
# expectations would be meaningless and the verdicts below would be noise.
echo "$all_ids" | LC_ALL=C sort -c 2>/dev/null || \
    die "the collected site ids are not in ascending order; the positional expectations below would be unreliable"
[ "$total" -ge "$MIN_SITES" ] || die "this organization has $total sites; reproducing needs at least $MIN_SITES (see the header)"
echo "  $total sites over $pages pages, verified ascending by id and free of duplicates"
echo

id_at() { echo "$all_ids" | sed -n "$1p"; }      # 1-based position in that order

# --------------------------------------------------------------- the evidence --
echo "CASE A (control) -- cursor = last id of page 1 (position $LIMIT)."
echo "                    Correct answer: the page starting at site $((LIMIT + 1))."
probe "start=<id at position $LIMIT>" "$(id_at $LIMIT)" "$(id_at $((LIMIT + 1)))"
echo
echo "CASE B (defect) -- cursor = first id of page 2 (position $((LIMIT + 1)))."
echo "                   Correct answer: the page starting at site $((LIMIT + 2))."
probe "start=<id at position $((LIMIT + 1))>" "$(id_at $((LIMIT + 1)))" "$(id_at $((LIMIT + 2)))"
echo
echo "CASE C (defect) -- cursor = the FIRST site id (position 1)."
echo "                   Correct answer: the page starting at site 2."
probe "start=<id at position 1>" "$(id_at 1)" "$(id_at 2)"
echo
echo "CASE D (control) -- cursor = the LAST site id (position $total)."
echo "                    Correct answer: an empty array."
probe "start=<id at position $total>" "$(id_at "$total")" "EMPTY"
echo

# ------------------------------------------- ONE failing request, headers + body --
# Headers and body come from the SAME response, so the status shown is provably the
# status of the body shown.
b_cursor=$(id_at $((LIMIT + 1)))
b_url="$API/organizations/$PANTHEON_ORG_ID/memberships/sites?limit=$LIMIT&start=$b_cursor"
b_raw=$(curl -s -D - -H "Authorization: Bearer $session" "$b_url") || die "the demonstration request failed"
b_status=$(printf '%s\n' "$b_raw" | head -1 | tr -d '\r')
b_date=$(printf '%s\n' "$b_raw" | tr -d '\r' | grep -i '^date:' | head -1)
b_body=$(printf '%s\n' "$b_raw" | awk 'body {print} /^\r?$/ {body = 1}')

echo "The failing request from CASE B, in full:"
echo
echo "  curl -s -D - -H \"Authorization: Bearer \$SESSION\" \\"
echo "    \"$b_url\""
echo
echo "  response status:   $b_status"
echo "  response $b_date"
echo "  expected first id: $(id_at $((LIMIT + 2)))   (the site after the cursor)"
echo "  actual   first id: $(printf '%s' "$b_body" | jq -r '.[0].id')   (the first site in the collection)"
echo "  elements returned: $(printf '%s' "$b_body" | jq 'length')"
echo
echo "Finished (UTC): $(date -u '+%Y-%m-%d %H:%M:%SZ')"
echo
echo "Any nonzero RETURNED-PAGE-1-AGAIN count above is the defect: a cursored request was"
echo "answered with the first page of the collection, HTTP 200, no error of any kind."
echo "('other' would mean a response that was neither the expected page nor the first page;"
echo "it should never occur, since every non-200 stops the script instead.)"
---------------------------- end reproduce-pagination-bug.sh -------------------

WHAT WE WOULD LIKE
------------------

Any one of the following would resolve this for API consumers:

1. Honor `start` for any valid site id in the organization, as the swagger
   description states -- i.e. return the sites ordered after that id.

2. If a supplied cursor cannot be honored, respond with an error (for example
   400) naming the problem, rather than returning the first page.  A loud
   failure is far less damaging than a plausible wrong answer.

3. Alternatively, document precisely which cursor values are valid, and return
   an explicit next-page cursor (or a `Link: rel="next"` header) in each
   response, so callers never have to construct one.

Two smaller things would help independently of which option you choose:

  * A stated total count for the collection, so callers can verify their own
    pagination rather than having to trust it.
  * A request-id (or similar correlation) response header.  There is none today,
    which is why this report can offer you only an organization id, a client
    string and a UTC time window to find these requests by.


WORKAROUND IN USE
-----------------

Pass `limit=100` and use as the cursor only the last id of the page just
received; stop when a page contains fewer than 100 items (never when it is
empty, per point 2 above).  Additionally, de-duplicate by site id and treat any
non-empty page that contributes no new ids as an ignored cursor: retry the same
cursor, and fail loudly rather than continuing, since the alternative is a
silently incomplete result.
